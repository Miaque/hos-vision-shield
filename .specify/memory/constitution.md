# Vision Shield Constitution

## Core Principles

### I. 聚焦媒体隐私打码与 RESTful 契约

项目必须以 Python 实现，通过 RESTful API 提供图片、视频和视频流中的人脸、车牌打码能力。
每项媒体处理能力必须定义输入、输出、失败语义与完成条件；不得把“请求已接收”等同于“处理成功”。
API 必须使用明确的请求与响应模型、HTTP 方法和状态码，并校验外部输入。
长时间运行的视频或流处理必须具有明确的任务状态、结果获取及停止方式。
路由层不得向调用方暴露模型库、解码器等底层实现细节。

### II. 全链路异步与非阻塞执行

请求接入、处理编排、外部 I/O 和结果交付必须遵循异步非阻塞执行模型。
具备异步接口的网络与存储操作必须使用异步调用；同步文件操作、模型加载、推理、
图像处理及视频编解码等可能阻塞的工作必须移出事件循环。
必须依据工作负载及库的线程安全约束选择受限的线程、进程或独立工作进程；
不得仅以 `async def` 包装同步操作宣称实现异步。

并发工作数和缓冲队列必须有上限；视频流必须定义背压或丢帧策略，禁止无限创建任务或缓存帧。
外部等待必须有超时边界，任务必须支持取消并回收资源。
验收必须验证媒体处理期间其他请求仍能获得响应，且并发压力不会导致队列无限增长。

### III. 模块边界与单一职责

代码必须按职责划分模块，至少明确 API 契约与路由、处理编排、人脸与车牌检测、
打码处理、媒体输入输出及配置与资源生命周期的归属。
上述职责可按实际规模组织文件，不要求为每项职责建立独立包或服务。
API 层负责协议转换与校验，编排层负责调用顺序和任务状态，
检测与打码模块负责处理逻辑，媒体适配模块负责读写及编解码。

模块必须通过明确的输入输出协作，禁止循环依赖，核心检测与打码逻辑不得依赖 Web 请求对象。
图片、视频及视频流必须复用适用的帧检测和打码逻辑，不得复制维护同一算法流程。
不得为了分层引入没有实际调用需求的接口、包装层或插件系统。

### IV. 最小实现与必要注释

实现必须限定在已确认需求内，优先复用现有模块、标准库和已安装依赖。
修改必须保持范围最小，不得顺带重构无关代码或引入预留扩展机制。
命名和函数拆分必须使主流程可直接阅读。

非直观的算法取舍、坐标转换、阻塞工作隔离、线程安全限制、背压策略及资源释放约束，
必须在相关代码处添加解释原因或不变量的注释。
跨模块公共接口必须通过类型标注及必要的文档字符串说明输入输出、坐标约定和副作用。
不得用注释重复显而易见的代码；修改行为时必须同步更新相关注释。

### V. 可验证的正确性与资源生命周期

新增非平凡处理逻辑必须有针对性测试；缺陷修复必须先建立可复现的失败用例。
测试必须覆盖实际变更涉及的人脸或车牌区域打码、无目标、无效媒体、处理失败和取消路径。
涉及异步调度的变更必须验证事件循环响应性及并发上限；
涉及媒体资源的变更必须验证正常结束、异常和取消后的释放行为。

输入文件、解码器、模型执行资源、网络连接和临时产物必须有明确的生命周期负责人。
错误必须可追踪且向调用方明确反馈；检测或打码失败时不得把未处理的原始媒体作为成功结果返回。
日志不得记录原始媒体内容、完整敏感访问地址或访问凭据。

## 技术与处理约束

- Python 为应用实现语言；具体 Web 框架、模型和媒体库由设计阶段依据上述原则选择。
- 图片、视频与视频流必须分别定义处理结束条件、资源限制及输出交付方式。
- 视频与视频流必须增量处理，不得依赖将全部帧预先载入内存。
- 检测框坐标与帧尺寸、缩放和裁剪的转换必须有统一约定，打码区域必须裁剪到有效图像边界。
- 对外部媒体输入必须定义允许的类型、大小或时长限制；流输入必须定义连接与读取超时。
- 接受远程媒体地址时必须校验协议和访问目标，防止服务被用于访问未授权的内部资源。
- API 文档必须说明支持的媒体、处理参数、结果格式和错误语义；不得宣称检测模型能保证零漏检。

## 开发与验收流程

1. 规格阶段明确媒体类型、目标类别、输入输出、失败行为及可验证的验收条件。
2. 设计阶段列出模块职责、调用方向、阻塞操作及其隔离位置，
   明确并发上限、背压、取消与资源释放策略。
3. 实现前检查调用方及相关配置、测试和契约；每个变更必须能追溯到已确认需求。
4. 验证阶段执行与变更匹配的测试，分别报告逻辑测试、真实模型和实际视频流验证的结果；
   不得把模拟测试通过表述为真实设备端到端验证通过。
5. 合并前审查 API 契约、事件循环阻塞风险、模块依赖、注释与资源释放；
   未满足的条款必须修复，或按治理流程形成有理由、有期限的明确例外。

## Governance

本宪章是项目设计、实现和评审的共同约束；规格、计划与任务必须在运行时读取并检查合规性。
本次首次采纳日期为 2026-10-18。

修订必须记录变更原因、受影响原则、兼容性影响及必要的迁移措施，并由项目维护者审查确认。
版本采用语义化版本：删除或不兼容重定义原则升 MAJOR，新增原则或实质扩充约束升 MINOR，
仅措辞澄清或修正升 PATCH。修订时必须同步更新版本、最后修订日期和同步影响报告，
首次采纳日期保持不变。

每项设计与代码评审必须检查相关条款，提供验证证据。
例外必须记录具体条款、理由、风险、负责人和失效条件，经项目维护者确认；
不得通过削弱测试、隐藏阻塞操作或静默跳过校验来满足交付要求。
