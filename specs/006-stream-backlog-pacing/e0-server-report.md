客户端保留4925条对应Pacer记录，另外3577条没有完整逐次样本；所有8502次仍计入累计计数。没有用保留记录的等待分布补造总体成本。内存环淘汰和字节预算省略各有计数；具体原因与时钟实例来自可配对保留样本。

一个具体实例：序号248、源时钟`992771 × 1/90000`，encoder为`917913 × 1/90000`。决策时刻5091702.4230244，当前due=5091702.4612497，请求38.225ms、实际等待38.314ms；保留防突发下限的条件due=5091702.4412572，重设增加约19.992ms请求，其余18.233ms仍受防突发约束。该帧本次没有重设，成本来自此前被抬高的计划基准，不能只统计执行rebase分支的当次wait。

## AAC与视频时钟异常

累计窗口记录 **54次AAC包raw PTS/DTS非递增**（第一窗口38、第二16），不是只在外部播放器PyAV解码观测中出现。worker的raw记录位于`read_source`、`LiveAVClock.audio_packet`之前；之后的normalized音频和提交mux的音频时钟均未记录非递增。

一个可配对实例（音频时基1/8000）：raw DTS从398471回退到397508，回退 **120.375ms**；既有修复将后一包改为399495，相对前一正常值推进1024 ticks，即128ms。没有改音频内容或新引入修复规则。

视频raw解码帧另有1次非递增；读线程修复后及主线程最终视频时钟未见非递增。正向PTS跳变仍存在，正常输出Pacer也记录了.5s间隔限幅次数，不能把这些事件误认为稳定40ms输入。

这些证据说明异常**确实到达了worker的输入时钟处理**，但还不能判定原始RTP时间戳、RTCP映射、连接/SSRC、解复用或解码中的哪个环节引入它；也不能认定100ms配置或播放器错误。没有同AU的AAC RTP/RTCP接收与worker包映射，未做默认配置覆盖对照。

## EOF、解码错误与重建边界

1. `5e724ccb…`正常`source_read/source_eof`、returncode=0。先观测到decoder drain包，再demux EOF。最后mux至下个attempt首mux为 **4.155328s**；内部实际接收空窗5.075s，二者分开。
2. `7b6e95fc…`为`source_decode_error`、`InvalidDataError`、errno=1094995529，FFmpeg原因为`Invalid data found when processing input`，returncode=1。调用链落在`packet.decode → VideoStream.decode → CodecContext.decode`。最后mux至下一次首mux **4.387080s**，内部实际接收空窗5.148s。没有原始包内容或设备trace，不能由错误码确定损坏发生位置。

正常EOF的4.155s可按已记录边界拆开：

| 区间 | 约秒 |
|---|---:|
| 最后mux→媒体E0结束（close/join完成） | .002 |
| E0结束→父进程media_execution_completed | **1.225** |
| 父进程publisher_close | .123 |
| close结束→retry开始 | .053 |
| 实际retry等待 | **1.001** |
| retry结束→下个worker attempt开始 | .042 |
| 新attempt开始→首有效mux | **1.709** |

1.225s包含最后报告、子进程协议收尾/事件消费及父进程状态处理，不能说成网络等待或GPU计算。新attempt的1.709s还包含source/publisher准备、打开源、首帧处理及前视暖机，不能全部称重连网络耗时。EOF之前，demux EOF到最后mux期间约.533s仍在释放安全尾帧，不属于最后mux后的空窗。

本轮由此进一步确认恢复成本包含应用生命周期和退避，但仍没有正常demux终止的底层协议原因。保留阶段一3.365/5.370秒及首轮4.063秒证据，本轮不替换或混算。

## 下一步最小方案与顺序

**优先处理计算/同步关键路径的独立实验；E1可作为幅度有限的单变量对照，E2不进入实现。**

- E1的具体变量已经收敛：仅取消`StreamPacer.wait`中“明显迟到则due=now”的计划重设，保留`max(previous_planned_due+d, previous_actual+d/2)`、.5s等待上限、停止打断及全部PTS/音频/前视规则。现有条件归因约7.7–7.9ms/帧，值得验证，但同内容真实运行的收益和前视补查变化尚未知。先更新这项政策所对应的节奏测试，跑实际音视频、场景切换、停止及恢复对照，再固定独立候选；不把本次授权自动用于一个尚未准备和验收的E1覆盖版本。
- 计算/同步实验只针对两处future的关键路径：在不改模型调用和工作量的前提下，关联submit、worker实际执行起止、future完成和主线程result起止，区分主模型排队、实际host forward及重叠不足；同一源内容与双流并发条件下验证。可先沿用现有stage区间和低开销调用身份，不新增逐帧CUDA同步或直接改模型。若另做设备采样，单独限定范围并报告扰动。
- 同内容E0开/关验证观测增量也应纳入独立受控方案，因为实机report路径已有可量化成本；关闭会重建应用，不临时修改服务器环境。
- 不把future等待直接删除，不调整人脸/车牌/LK质量策略，不扩大队列。只有计算关键路径与E1都不足、且真实音视频和最终帧生命周期证明正确后，才考虑发布线程。

本轮完成了E0部署与具体成本归因，**没有完成持续积压修复、播放器缓冲验收或AAC根因归属**。当前服务器保留E0/100ms候选，后续任何行为候选仍先提交固定commit、影响及恢复方式。
