# 功能规格：服务器 CPU/GPU 部署与离线模型

**功能分支**：未新建；规格目录与分支独立，编写时位于 `main`。

**创建日期**：2026-10-19

**状态**：CPU/指定单卡 GPU Compose、离线模型预检与配套实现已生成，本地回归已执行；后续服务器分阶段实测见[时序优化记录](temporal-optimization.md)，完整部署与效果验收仍待部署人员完成。2026-10-19 用户确认沿用线上已有 Docker/Compose，不在本机安装 Docker，由用户执行服务器命令。本机实现记录见 [local-gpu.md](local-gpu.md)，本次证据见 [实施记录](validation/gates.md)。

**输入**：GPU 版本已经开发完成，现在通过 Docker Compose 部署到服务器环境，可选择 CPU 或 GPU 运行并查看效果；依赖模型必须离线提供。沿用此前已确认的图片、视频和 RTSP 效果及性能验证、保留本机运行方式、镜像允许联网获取、GPU 不可用不得静默回退 CPU 等约定。

## 用户场景与测试

### 用户故事 1 — 使用离线模型部署 CPU 服务（优先级：P1）

部署人员在没有 GPU 的环境准备模型包，按部署说明启动完整服务，提交图片和视频并获得脱敏结果。

**优先级理由**：无需 GPU 即可验证交付物、模型准备和基本处理链路。

**独立测试**：在无 GPU 环境准备镜像与离线模型包，禁止访问外部模型来源后启动服务，提交一张图片和一个视频，下载并检查结果。

**验收场景**：

1. **给定**完整离线模型包和必要运行环境，**当**选择 CPU 并启动，**则**服务可以处理媒体，无 GPU 要求，也不下载模型。
2. **给定**缺少、损坏或不可读的必需模型，**当**启动，**则**对应处理能力不得报告就绪，错误指出问题文件及修复方向，不自动下载或换用其他模型。
3. **给定**已生成的结果和任务记录，**当**正常停止并重新启动部署，**则**已完成结果和记录仍可获取，在途任务遵守既有失败与恢复语义。

### 用户故事 2 — 在服务器选择 GPU 处理（优先级：P1）

部署人员在受支持的 GPU 服务器选择 GPU 模式，在相同检测策略和模型下处理媒体，并确认哪些推理环节实际使用了 GPU。

**优先级理由**：提供用户所需的另一运行方式，并避免名义上启用 GPU、实际仍全部使用 CPU。

**独立测试**：在目标服务器使用与 CPU 相同的模型和输入执行任务，核对实际推理设备；另在无可用 GPU 的环境选择 GPU 验证明确失败。

**验收场景**：

1. **给定**受支持的 GPU 及完整模型包，**当**选择 GPU 启动，**则**实际执行 GPU 推理，并能查看各检测环节的实际设备。
2. **给定**GPU 不存在、不可访问或运行环境不兼容，**当**选择 GPU，**则**受影响处理能力明确失败且不报告就绪，不静默改为 CPU。
3. **给定**相同模型、检测策略及参数，**当**停止部署后切换 CPU/GPU 模式，**则**无需修改应用源码，不隐式改变检测策略、输入输出契约或历史结果。
4. **给定**服务器有多张 GPU，**当**部署人员通过卡号或 UUID 指定其中一张并处理文件与流任务，**则**两类任务仅使用指定 GPU，不自动使用其他卡；指定设备无效时明确失败。

### 用户故事 3 — 对比真实媒体效果与处理速度（优先级：P2）

使用者通过同一组媒体对比两种模式，查看实际遮挡效果和处理速度，判断是否适合目标服务器。

**优先级理由**：部署启动成功不能证明媒体可用或 GPU 带来收益。

**独立测试**：分别以两种模式运行同一图片、视频及可重复播放的 RTSP 素材，保存结果和测量记录。

**验收场景**：

1. **给定**具有可人工核对人脸和车牌的固定素材，**当**分别执行两种模式，**则**保存可查看的脱敏输出，并记录漏遮、误遮及两种模式的差异。
2. **给定**相同输入与处理参数，**当**对比性能，**则**记录硬件、模型版本、实际设备、输入尺寸、并发数、启动/首次处理耗时及后续处理耗时；视频和流另记录处理帧率，流记录观察时长及丢帧情况。
3. **给定**服务器提供的脱敏流，**当**同一允许网络中的客户端播放并请求停止，**则**播放地址可达、画面可查看，停止后处理资源得到释放。

### 边界情况

- 模型包不完整、校验不匹配、目录不可读：阻止相关处理能力就绪，并指出问题；禁止联网补齐。
- 显式 GPU 模式下设备不可用或显存不足：明确报告启动或任务失败，不降级为另一设备或检测策略，不交付未脱敏媒体作为成功结果。
- 显式 CPU 模式运行于有 GPU 的机器：仍按 CPU 模式执行，不自动切换。
- 指定的 GPU 卡号或 UUID 无效、设备不可访问：明确失败，不自动改用另一张卡；选择某张卡不代表对该卡的独占或显存容量保证。
- 重启、流源断开和停止任务：保持既有恢复与取消约定，不因容器部署改变任务含义。
- 服务内部可访问但用户无法播放：不能算流验收通过，须从允许网络的客户端实际播放验证。
- 两种模式存在数值或遮挡差异：记录差异，不要求逐像素一致，也不据模型成功加载宣称零漏检。

## 需求

### 功能需求

- **FR-001**：必须提供 Docker Compose 服务器部署入口，涵盖请求接入、任务协调、文件与流处理以及必需的状态和媒体服务；部署文档包含准备、启动、检查、停止和重启步骤。（故事 1、3）
- **FR-002**：必须支持显式选择 CPU 或 GPU；设备选择与检测策略独立，不通过更换检测算法实现设备切换。默认保持现有效果优先策略。（故事 2）
- **FR-003**：CPU 模式不得要求存在 GPU；GPU 模式必须实际使用 GPU 执行检测推理，并披露仍在 CPU 执行的环节。加速环节和兼容范围由规划阶段依据模型与硬件确定，不承诺所有环节均使用 GPU。（故事 1、2）
- **FR-004**：用户必须能独立准备和传输离线模型包，包含所选策略全部必需模型、版本、来源、许可证说明及完整性校验信息；复用现有固定模型，不重新选型。（故事 1）
- **FR-005**：模型必须从部署人员提供的本地文件加载，启动和处理均不得自动下载；就绪前必须检查模型完整性、可读性及可加载性，失败须给出明确诊断。（故事 1、2）
- **FR-006**：显式 GPU 不可用时不得静默回退 CPU；模型加载或运行失败时不得静默更换检测策略，也不得将未处理媒体作为成功结果。（故事 2、边界情况）
- **FR-007**：必须保留现有媒体任务的输入输出、状态查询、结果获取、停止、失败和恢复语义；正常重建或重启部署不得丢失应保留的任务记录、结果或模型。（故事 1、3）
- **FR-008**：必须说明用户可访问的服务地址、流播放地址及必要的网络配置；内部状态与控制服务不得因部署默认向外部网络开放。沿用既有媒体来源限制和访问边界。（故事 3）
- **FR-009**：必须提供可重复的效果与性能验收步骤，覆盖图片、视频、RTSP，按两种模式保存结果和记录；必须区分配置检查、模拟测试、真实 CPU 验证和服务器真实 GPU 验证。（故事 3）
- **FR-010**：必须保留现有 Windows 本机 CPU/GPU 运行方式及其设备选择约定；复用已实现的设备选择能力，不以本机 GPU 验证替代服务器容器 GPU 验收。（故事 1、2）
- **FR-011**：单套 GPU 部署必须由部署人员通过卡号或 UUID 显式指定一张 GPU，文件与流任务共用该卡，不自动使用其余卡；指定设备无效时明确失败。本次不实现多卡任务调度。（故事 2、边界情况）

### 关键实体

- **离线模型包**：部署所需的固定模型文件及其身份、来源、许可和完整性说明；被部署实例加载，不由业务请求获取。
- **部署实例**：一套选定设备模式、检测策略及服务地址的运行环境，关联自己的任务状态和结果存储。
- **验收记录**：关联固定素材、模型、设备、参数、输出和测量条件的一次验证结果，用于复现和对比。

## 成功标准

### 可衡量结果

- **SC-001**：无加速设备环境按文档完成部署，至少一张图片和一个视频成功处理且结果可查看；在阻止访问外部模型来源后，启动和处理仍成功，模型下载尝试为 0。
- **SC-002**：两种设备模式分别完成至少一张图片、一个视频和一段持续至少 60 秒的流验证，共六组记录；每组均关联实际设备、模型、输入和可查看的输出。
- **SC-003**：至少覆盖缺模型、模型校验失败、模型不可读和所选加速设备不可用四类错误；四类均明确失败且无静默回退或虚假就绪。
- **SC-004**：两种模式的图片与视频均记录一次首次处理以及至少三次后续处理的耗时，并报告后续处理耗时中位数；流记录至少 60 秒的处理帧率与丢帧情况，不预设未验证的加速倍数。
- **SC-005**：两种模式各完成一次服务停止与重启，已完成任务及结果可获取；各完成一次流停止，确认任务停止并释放处理资源。
- **SC-006**：六组效果记录均具备人脸与车牌的人工核对结果；所有发现的漏遮、误遮和模式间差异被明确记录，不把成功运行视作检测准确率保证。
- **SC-007**：在具有多张加速设备的目标服务器指定其中一张，至少一项文件任务和一项流任务实际使用的加速设备均与选择一致；另以一个无效设备标识验证明确失败，未改用其他设备。

## 假设与范围

- 已确认目标为 `hos-vision-shield`，不修改 Event Hub；采用模型离线、镜像允许联网获取的边界，不交付整套离线镜像仓库或离线系统依赖安装方案。
- 使用现有模型组合及阈值，不新增识别能力、不重新训练、不增加管理界面，不扩大为多机调度、多卡任务分配或多 GPU 性能优化；用户已确认先单卡验证效果，具体卡号或 UUID 在部署时指定。
- 设备切换通过停止并重新部署生效，不要求运行中的任务热切换设备。GPU 模式允许部分处理环节继续使用 CPU，但必须明确说明并可核验实际 GPU 推理。
- 用户提供的目标服务器信息为 Ubuntu 24.04.4 LTS、x86_64、7 张 NVIDIA RTX 6000 Ada Generation，每张报告显存 49140 MiB，驱动 595.84；替代此前 aarch64 意向，本次不扩展 ARM64 或 Jetson 支持。以上为用户提供的命令输出，尚未由本次部署实测核验。
- 目标服务器已有 Docker Compose v2.29.2，可用入口为 `docker-compose`，`docker compose` 子命令不可用；交付说明须适配当前入口，不要求仅为命令形式而更换安装。Docker Engine 版本及 NVIDIA 容器运行时是否已配置在部署预检时核验，不把宿主机能运行 nvidia-smi 视为容器 GPU 已可用。
- 验收素材由现有样例或用户有权使用的素材提供；流对比使用同一固定素材作为可重复流源。性能对比尽量在同一服务器、相同输入与并发条件下进行，无法一致时显式记录差异。
- 已有 Windows 本机运行文档在实施阶段保留，并同步补充服务器部署说明；本规格不改变现有对外接口或模型效果承诺。
