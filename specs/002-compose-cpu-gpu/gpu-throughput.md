# GPU 模式下的补充检测并行优化

日期：2026-10-20。基线为工作区原有 GPU 调度优化版本，硬件仍为本机 Intel i5-10400 / GTX 1080 8GB，PyTorch 2.14.1+cu126、OpenCV 4.14.0。没有在服务器 RTX 6000 Ada 上测量。

## 改动与约束

GPU 模式原来已经重叠执行 EgoBlur 与 CPU 补充检测，但每个补充检测视图内的 YuNet、HyperLPR 仍串行执行。3840×1080 输入有全图和 16 个重叠分块，每帧执行 34 次 CPU 模型调用，局部复核另计。

本次仅在 `quality` 的 CUDA 模式中，并行执行每个视图的 YuNet 和 HyperLPR。两个独立模型各执行一路，按原有人脸、车牌顺序合并结果；每个视图结束或失败时等待后台工作结束，然后才处理下一视图或局部复核。任一路失败仍使任务失败，不返回部分成功结果。并行任务有界，不新增常驻线程池。

四份权重、FP32 推理、模型后端、预处理、最长边 1280、阈值、分块、扩框、局部复核、200 毫秒历史框补偿、逐帧视频处理和编解码均保持原有设置。Torch 仍为 4 线程，OpenCV 仍为 2 线程；CPU 模式保持串行。没有新增依赖或环境变量。

## 交错试验

使用用户提供的 3840×1080、120.44 秒车牌视频在 0 秒、60 秒处的画面及既有人群图。四轮交错运行，排除首轮，取后三轮中位数。仅计检测，不包含模型初始化、编解码、哈希核对或 API/队列。

| 输入 | 优化前秒 | 优化后秒 | 耗时减少 |
| --- | ---: | ---: | ---: |
| 车牌视频 0 秒 | 1.503 | 1.064 | 29.2% |
| 车牌视频 60 秒 | 1.516 | 1.045 | 31.1% |
| 人群图 | 1.889 | 1.483 | 21.5% |

上述三幅输入的检测框、顺序、坐标和完整遮挡像素一致。

尝试记录：单独将 OpenCV 改为 4 或 6 线程，三个样例分别降低约 13%～19%、19%～26%，部分坐标出现微小浮点变化。保留原 2 线程并并行两个独立模型，在这三个样例上收益更大，也避免新增服务器线程数校准参数；没有将加线程与并行叠加。未迁移模型后端、降低精度、抽帧或使用跟踪近似。

## 固定集合验证

优化前从开始本次任务时保存的 `quality.py` 加载，调用原调度路径；优化后调用当前生产实现。每份素材交错选择先后顺序，两个实例分别加载相同权重，任务并发为 1。图片调用 `process_image`，视频调用 `process_video`。

| 范围 | 优化前秒 | 优化后秒 | 耗时减少 |
| --- | ---: | ---: | ---: |
| 全部 16 张图片 | 16.568 | 12.663 | 23.6% |
| 5 段既定片段、104 帧 | 96.147 | 76.178 | 20.8% |

此表为单批次测量，包含解码、检测、遮挡、编码及两边相同的逐帧框/像素哈希采集开销；不含模型初始化、进程启动、API、队列和网络。不能当作无采集开销的端到端吞吐，稳定收益另由上方交错试验确认。

16 份 JPEG 和 5 份 MP4 逐字节一致；104 帧编码前遮挡像素一致，输出帧数、尺寸和源时间戳一致。扩展集合发现部分 CPU 检测坐标随并行调度产生微小浮点波动，不能宣称全集浮点坐标逐位一致。验收要求框数量和顺序对应、坐标绝对误差不超过 0.001 像素，同时完整遮挡像素哈希和结果文件哈希必须完全相同；像素和文件不使用容差。

实际固定集合中 19/21 份素材的浮点框完全相同，另外两份最大坐标差为 0.0002381 像素，最终遮挡像素和文件仍完全一致。已匹配到的 21 处标注遮挡/保留区域通过；标注只覆盖部分目标和已知误遮区域。

另直接解码用户原视频，在 0 秒、60 秒、118 秒处各连续处理 15 帧，两边分别重置 `FrameRedactor` 并使用相同源时间，完整比较每帧包含历史框补偿的 RGB 画面：45/45 帧像素哈希一致。检测及遮挡累计 70.453 → 50.553 秒，减少 28.2%；此项不包含解码、编码、哈希和模型初始化，不是完整 MP4 任务端到端计时。没有把原视频全部加载到内存；原文件处理前后哈希一致，四份模型哈希也保持一致。

自动化测试先复现独立模型无法重叠执行的失败，再验证并行返回顺序、只读输入、非法模型输出和任一路失败后回收后台工作。完整单元测试、视频管线及真实 GPU 用例共 154 项通过；GPU 用例在明确亚像素容差且保留像素完全一致断言后另行重跑，同时补验两项真实媒体子进程生命周期用例。

## 本地证据与部署

原始记录位于 Git 忽略目录 `data/validation/gpu-throughput-20261020/`：

- `probe.py`、`probe.json`、`probe-summary.json`：交错试验与所有尝试。
- `verify.py`、`verification.json`：逐素材计时、原始素材/权重/源码哈希、检测框及遮挡像素、输出文件核对。
- `coordinate-difference.json`、`serial-stability.json`：坐标差异和原串行路径重复推理诊断，不把微小浮点差异隐藏为精确一致。
- `gpu-lifecycle-tests.log`：最终真实 GPU 与两项媒体子进程生命周期验证日志。
- `*-baseline.py`：开始优化时保存的原实现。

服务器需要使用新源码重新构建并重启 GPU worker 后生效，部署步骤沿用 [部署验收指南](quickstart.md)。运行中的旧媒体进程不会热加载此改动。先用同一视频、同一 CPU 配额和并发负载比较 `processed_frames / elapsed_seconds`；本机收益不代表 RTX 6000 Ada 的实测收益。

本轮不构成完整两分钟原视频、服务器 Docker、多任务并发或真实 RTSP 验收。历史 `rtsp-green` 素材仍缺失，不能把完整历史质量集合标为通过。

## 后续构建缓存修复

旧 Dockerfile 在复制源码后安装全部依赖，且最终镜像整体复制已经安装应用的虚拟环境，源码变更会同时使依赖安装和大依赖打包层失效。本次调整为独立 dependencies 阶段安装锁定依赖、builder 阶段生成应用 wheel、运行阶段复用依赖虚拟环境并单独安装 wheel。依赖下载和 wheel 构建使用 BuildKit 的 uv 缓存挂载，uv 工具及缓存不复制到运行镜像。

依赖清单、构建参数和基础镜像不变，且同一 builder 保留缓存时，仅改源码或 README 可以复用依赖层。第一次切换分层结构仍须建立新的依赖层；依赖文件变化时也需要重新执行依赖安装。这与 [Docker 分层建议](https://docs.docker.com/build/cache/optimize/)及 [uv Docker 集成](https://docs.astral.sh/uv/guides/integration/docker/#intermediate-layers)一致。

缓存修复单独提供 `data/validation/gpu-throughput-20261020/docker-cache.patch`，仅修改 Dockerfile，可在先前 GPU 优化补丁之后应用。两项部署依赖/缓存分层测试通过；缺少源码和 README 的 CPU Linux 依赖 dry-run、GPU Linux 哈希锁 dry-run、实际 wheel 构建及无依赖安装 dry-run 均通过。已核对 wheel 内两份优化源码字节一致；未修改本机虚拟环境。本机未安装 Docker，实际镜像构建及 `CACHED` 命中需在服务器验证，不能将这些检查当作 Docker 实测。
