# P2：最终安全帧发布线程的最小原型

## 要回答的问题

独立发布线程能否让已经完成复核、前视补遮和最终遮罩的画面，在下一帧模型处理阻塞时继续发布？队列满或超预算时，是否能保守阻止输出并向任务所有者报告？

本地可运行实验：

```powershell
python specs/004-live-tail-continuity/experiments/final-queue-prototype.py
```

这是单生产者的可丢弃原型，不被应用模块导入，也没有部署到媒体链路。`FinalFrame` 的调用方合同是仅由既有 `PlateLookahead` 返回的最终 render 结果创建，不能包装待未来确认的帧。原型拒绝普通原始对象；类型本身不能证明像素已脱敏，正式接入必须在真实返回点完成这个边界。

## 状态与预算

- 最多 4 个最终帧，单帧仅保留已完成的像素、序号、原 PTS 及完成时间。
- 入队等待最多 0.5 秒；队列满向调用方报告超时，帧仍由调用方持有。
- 最终帧就绪到发布的预算 0.5 秒，包含队列和 pacing 等待；超时阻止后续输出并报告，不放行原始帧、不重复帧或改 PTS。
- 独立发布者复用 P1 的媒体节奏控制，发布回调异常回传任务所有者。
- 正常帧、保护帧、丢弃帧及阻止输出分别计数。该原型只评估阻止输出策略，没有约定新增整帧保护策略，保护帧及丢弃帧为 0。
- 发布回调自身如果不返回，Python 线程不能保证回收；close 在预算后报告需要回收进程。正式路径仍必须依赖有超时的 I/O 和现有受控子进程退出确认。

## 本地自检结果

| 场景 | 发布结果 | 最大队列 | 保护/丢弃 |
| --- | --- | ---: | --- |
| 生产者阻塞、已有 4 个最终帧 | 独立线程继续发布，4 帧、顺序和 PTS 一致 | 4 | 0 / 0 |
| 原始/未确认对象入队 | 明确拒绝 | 0 | 0 / 0 |
| 最终帧过期 | 0 帧发布，报告预算超时 | 1 | 0 / 0 |
| 发布回调失败 | 0 帧记为成功，异常回传 | 1 | 0 / 0 |
| 容量 1、发布者阻塞 | 入队超时、未接纳帧保留在调用方，已过期排队帧阻止输出 | 1 | 0 / 0 |
| 已关闭发布者再次提交 | 明确拒绝 | — | 0 / 0 |

## 结论与真实接入边界

原型证明有界最终帧队列可以隔离后续模型阻塞，但只能发布已经安全完成的存量帧。若队列里仅有 4 帧，25 FPS 下仅约 160ms 可播放内容，无法覆盖 1.6 秒模型长尾；增加缓冲本身又增加延迟。0.5 秒前视加 0.5 秒发布预算并非 0.5 秒端到端延迟。

真实 GPU render 已分配独立遮罩输出并同步，但发布线程仍需验证 CUDA context、DLPack 存储生命周期、NVENC 及唯一 mux 所有者、音频与视频包的共同排序、错误/停止回传和进程回收。必须同时约束帧数及 GPU 显存/音频字节预算。不能只把当前 `write_output` 交给线程池，因为它共享编码器、音频、报告计数、容器及关闭生命周期。

本轮保留 P0/P1 的独立候选与 P2 调度实验，不据此声称真实 GPU 发布已经解耦。是否正式接入，取决于持续实测中的处理长尾和积压证据；任何接入都需要另一轮真实媒体及 RTX 双流验证。
