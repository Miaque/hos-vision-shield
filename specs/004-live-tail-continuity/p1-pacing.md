# P1：最终安全帧的发布节奏

## 复现与最小改动

原 `PlateLookahead` 在场景切换调用 flush，或处理长时间阻塞后调用 expire，都会返回多帧。`process_stream.release` 在同一处理循环连续编码这些帧，没有独立播放时钟。前视补遮本身已存在，本轮不修改它的检测、反向定位、补查或最终遮罩规则。

新增 `StreamPacer`，仅在实时 CUDA/flow 前视路径、帧已完成 render 后、编码提交前使用。视频时间间隔决定最小发布间隔；实际提交迟到时，以当前时钟继续，迟到不为后续帧积累追赶额度。单帧等待最多 0.5 秒，停止事件可中断等待。没有增加另一个帧队列，既有前视容量 16 帧及输入 FIFO 容量保持不变。

`STREAM_OUTPUT_PACING=false` 关闭节奏控制，Compose 与本机环境均可配置。媒体 PTS/DTS、帧序、音频包、检测工作与遮罩决策不由 pacer 改写；文件处理不启用该等待。

## 本地验证

真实 `PlateLookahead`、零模型耗时、15 FPS、40 帧、第 20 帧场景重置：

| 指标 | 原连续发布 | 启用节奏控制 |
| --- | ---: | ---: |
| 前视一次完成的最大批量 | 8 | 8 |
| 实际发布最小间隔 ms | 0 | 66.667 |
| 实际发布最大间隔 ms | 533.333 | 66.667 |
| <1ms 的间隔数 | 15 | 0 |
| 完整帧数、顺序、PTS | 40，正确 | 40，正确 |

回归先以无节奏控制的实现复现失败，再实现等待并通过。另覆盖 2 秒处理阻塞后不集中追赶、场景切换补查遮罩保留、等待预算和停止、关闭开关时的真实流路径。现有故障关闭、输入时钟、音频及 CUDA 路径测试继续通过。

完整 unit：859 通过、96 项既有 GPU 用例按条件跳过。另显式运行真实 NVDEC/遮罩/NVENC 的 RTSP/RTMP AAC 输出 2 项，静音/AAC/VFR/推理故障关闭媒体 4 项，共 6 项通过。服务端真实模型连续性对照尚待执行，不能以确定性测试宣称所有卡顿已消失。

## 边界

当前仍由同一线程处理模型和发布。新的慢复核依然可以阻塞已安全完成帧的输出；本改动只控制恢复后的发布节奏。处理能力持续不足时，保持全部帧且不快进必然增加延迟，不能声称单靠 pacing 同时保证固定总延迟。

P2 需独立评估有界最终帧队列与发布线程，不将未完成前视补遮的帧提前加入队列；也不能为了隐藏积压改 PTS、重复帧或静默丢弃历史画面。

## 现场替代流

原 G3 后来在 source_open 连续失败，未进入模型链路。用户要求停止该任务后，API 已确认原任务 `86ecd4f1-0afe-4065-a91b-af616c21420d` 为 stopped。用户在部署白名单中追加回放主机后，以 P0 标签重新部署生效，创建替代任务 `3c66326a-fd00-4fc8-9e99-9af23fbe45b7`，输入为用户指定 `rtsp://192.168.1.104:8555/replay/rfm-01`，3/flow、solid、保留音频。服务端确认 running/ready 且有实际输出；本机直连 RTSP 的 5 秒探测超时，未据此宣称客户端播放已验证。替代流不是 G3 原始实时源，后续双流报告必须标注这一点。
