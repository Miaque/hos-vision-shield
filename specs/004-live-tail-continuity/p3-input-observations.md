# P3：W 型输入异常的独立记录

## 已有证据与本轮范围

此前独立原始 RTSP 对照观察到约 1.73 秒接收空窗；它不能单独证明故障在摄像头。PotPlayer 在另一台电脑播放流畅，也不能排除服务器接入、缓冲或读取路径异常。

本轮遵守服务器权限边界，仅通过用户允许的业务 API 读取任务指标及已有错误摘要，没有新增服务器抓包、额外 SSH 探测、传输协议切换或网络配置变更。

W/rfm 任务 `d22ec295-615f-4ef6-8f22-5c143f63557d` 的近期记录同时包含：

- `source_eof / source_read`：来源连接结束后重连。
- `source_read_error / source_read / ConnectionResetError / errno=104`，安全错误文本为 `Connection reset by peer`。
- 部署引发的 `worker_shutdown / worker_control`，必须与自然来源断连分开统计。

第一轮 P1 窗口中，rfm 在一个连接片段出现约 7.20 秒应用接收间隔及 6.39 秒输出间隔，随后进入新连接。此时不能把所有停顿归因于局部人脸，也不能仅据这些指标认定摄像头或网络故障。

API 的 `received_monotonic` 是应用 demux/读取路径中的时刻，输入 FIFO 背压可阻止进一步读取，不能直接称作网卡收包时刻。历史 `attempts_discarded` 是任务累计淘汰数，不是本轮新发生的失败次数。

## 替代回放源的时钟

用户指定回放替代 G3 后，本地原文件检查发现：rfm-01 原录像 2208 帧、640×480、时长 91.937 秒，平均约 24.02 FPS；有 60 个小于 10ms 的原始 PTS 间隔，最小 0.0625ms，最大 PTS 间隔 2.975 秒。极短间隔在 RTSP 回放输出也可观察到。它们是已有媒体时序，不能归咎于 P1 发布器；也不能改 PTS 或重复/隐性丢帧来证明连续性达标。

替代任务的历史还观察到 `source_decode_error / InvalidDataError` 与 `source_eof`，因此回放服务到接收端的链路也未完成稳定性验收。这不改变原 W 型问题的归属，两个来源分别记录。

## 当前结论与下一步

可以确认存在输入读取/连接生命周期异常，尚未定位到源端发送、网络、RTSP 服务、客户端缓冲、解码或应用背压中的具体一层。本轮没有修改重连规则或降低检测质量以掩盖它。

进一步定位需要同一来源地址、相同 TCP 协议、相同时段的服务器侧低开销原始收包、解复用、解码和应用读取对照，并与发布背压关联。该类额外服务器诊断命令未获本轮通用授权；如果后续需要执行，须给出具体命令和影响范围，再取得相应授权。当前已授权的部署脚本不能用来夹带抓包或远程探测。

本地证据为实验目录中的 `p3-api-attempt-evidence.json`、`p0-replay-dual-90s.json`、`p1-replay-dual-90s.json`；这些指标与保留错误不构成根因已解决的证明。
