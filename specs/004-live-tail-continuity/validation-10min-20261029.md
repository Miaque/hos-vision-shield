# 2026-10-29 双路 10 分钟实测

## 结论与范围

按用户要求重新采集完整 600 秒，不重跑 30 分钟。时间为客户端 UTC+8 14:08:09–14:18:09；业务 API 查询 488 轮，资源快照 99 轮，API 查询失败 0 次。逐次查询先将新增帧及指标写入并 flush 到 JSONL，再输出进度；最终明细与日志输出帧合计核对一致，共 23,051 帧。

本次仅使用 `http://127.0.0.1:18000` 查询任务、既有诊断及资源，没有部署、修改配置、重启或创建任务，也没有运行其他 GPU 诊断负载。最近一次本任务成功部署的标签为 `cand-20261029-live-pacing-p1-03 / 1b38c9d`；本轮没有通过额外服务器命令重新读取部署版本。

**连续性与延迟验收仍未通过。** W/rfm 在本窗口没有 >500ms 输出停顿，但有效输出低于 25 FPS，并出现相对媒体时钟的延迟累积。替代回放流低于 15 FPS，发生两次 EOF 重连和多次较长输出间隔。两路都不能只凭平均 FPS 或有界输入队列判定实时性达标。

## 长停顿与内部不均匀

回放的两个最长输出间隔为 3.576s 和 3.274s，对应 `source_eof / source_read` 后的新连接，API 保留了各自 attempt ID 与结束时钟。另一次同连接内 2.059s 输出间隔，对应按输出帧配对的应用读取时刻差约 2.910s。

但不能把全部停顿归为来源：回放另有约 805ms、792ms、779ms 输出间隔，对应的应用读取时刻差约 52ms、40ms、43ms；W/rfm 的最大 444ms 输出间隔对应约 45ms。内部处理、前视等待、背压或发布仍可能贡献不均匀，需要继续分段验证，不能由本轮断言是某次局部人脸 run 或某个 GPU 算子。

`received_monotonic` 是应用解复用读取路径中的记录，按帧 PTS 关联；它不是网卡收包时间，解码重排下相邻输出帧对应的读取时刻也可能不单调。EOF 也不能单独定位到摄像头、网络或 RTSP 服务。

W/rfm 同一连接的输出墙钟跨度减媒体跨度为 **+19.08s**。回放三个连接片段分别为 **+42.11s、+103.14s、+62.63s**，不能将跨重连片段简单相加作为摄像头到播放器总延迟。回放本轮还有 220 个样本沿用既有异常时钟修复，解释其媒体跨度时须同时保留这个条件；W/rfm 没有时钟修复样本。

这些数值确认输出时钟相对媒体时间出现累积，不能直接给出绝对端到端延迟。即使应用读取至输出大部分约 0.7–2 秒，TCP、解复用或来源缓冲仍可能藏有更早积压。输入 FIFO 最大 2 帧不等于整个链路没有积压，500ms 前视窗口也不等于 500ms 总延迟。

按 PTS 关联的应用读取到解码返回间隔，回放 P95 约 802ms、最大约 2094ms；这包含包/帧重排、期间读取及背压等待，不能当作纯 NVDEC 执行耗时。W/rfm 对应 P95 约 0.636ms。仍需受控对照才能进一步确定差异来源。

## 资源与计数

- 整卡 GPU 利用率 P50 / P95 / 最大：50% / 70.1% / 85%；显存最大约 7.09 GiB。按 GPU UUID 每轮取一份整卡数据，不将多个 worker 的同一显卡数值相加。约 5–6 秒的采样不能排除更短尖峰。
- 两个 streams worker 的 CPU P95 约为单核的 258% 与 155%，峰值约 273% 与 160%；容器限额均为 80 核，不能解释为整机占用 258%。内存峰值约 2.10GB、2.26GB，首尾变化约 -0.11MB、+5.51MB；这 10 分钟不足以证明不存在长期泄漏。
- 观察到的失败帧、保护帧计数均为 0。W/rfm 的丢弃计数维持 1→1，没有新增；这是此前已存在的首帧无 PTS 丢弃。回放各连接丢弃计数均为 0。重连边界无法由当前采样证明所有输入帧都已发布，不能把“样本序号连续”扩张为整个原始源完整性证明。
