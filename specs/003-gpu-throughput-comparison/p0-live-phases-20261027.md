# 实时分段时刻诊断（2026-10-27）

上一轮 rfm 出现约 5.943 秒输出间隔，同区段读包累计等待约 5.994 秒，
但不能由现有包接收时刻区分解码重排/释放等待与处理排队。相关证据见
[现有双流进度](current-progress-20261027.md)。本轮只补齐该缺口，未替换模型、调度、遮罩或媒体策略。

## 要回答的问题

1. 长时延是否已经发生在包到达至解码器返回帧对象之间？
2. 解码返回后，帧是否在 FIFO 或主线程调度处等待？
3. 开始处理至成功 mux 是否才是停顿主要来源，混合文件负载如何影响它？

## 最小实现与口径

仅 DEBUG 记录解码返回与开始处理两个单调时刻，经原 FIFO 元数据、按 PTS 索引的
编码 pending 表传至成功写出样本。事件继续使用 task_id、attempt_id 和 sequence 关联；
不新增逐算子同步、日志、依赖、线程、请求参数或诊断端点。非 DEBUG 不采集这两个时刻。
输入视频宽高随原 DEBUG stream 统计返回，以核实当前较小播放输出的输入条件。

解码时刻位于 `packet.decode()` 返回后，表示帧对象已由解码器释放，不表示 GPU 完成同步。
处理时刻位于 FIFO 取出后、时钟处理和脱敏前；至成功 mux 的阶段包括时钟处理、GPU 等待、
预处理、模型、跟踪、遮罩和编码/推流，不把它命名为纯模型耗时。
原 received_monotonic 仍是对应视频包从 demux 返回的时刻，可能早于实际解码释放很久。

分析器增加 receive_to_decode、decode_to_processing、processing_to_output 的 nearest-rank
P50/P95/P99 及有效分段样本数。缺少新字段的旧证据保持可读，阶段分位为 null，不能补造为零。
非有限、逆序或只有一个新时刻的样本记录 invalid_phase_clock，不作计时验收通过判断。
不能将各阶段分位数直接相加作为总延迟分位数。

## 本地验证

新回归先在原实现上失败，修正后 83 项定向检查通过，覆盖延迟编码关联、FIFO 帧时刻、
CUDA 失败关闭、旧样本兼容、API 序列化、非法/缺失阶段时刻与完整 512 样本进程管道传输。
完整样本事件仍低于现有 256 KiB 行限额，无需提高管道上限。
媒体输出、音频时钟及 attempt 结束回归 162 项通过、96 项按既定 GPU 条件跳过。
另显式运行两项真实 NVDEC/遮罩/NVENC（含 B 帧输入、RTSP/RTMP 及 AAC）和一项
隔离 Redis/API 传递检查，3 项通过。输入宽高在真实 GPU 与 CUDA 契约检查中均保持。

以上是本地观测传递及媒体契约证据。以下另列部署后的 RTX 结果，不将两类证据混用。
