## 当前目标与不可变约束

目标是在 RTX 6000 Ada 上提高路线 A 的实际处理能力。固定负载是两路实时流常驻，
同时至少两个文件任务在 GPU 上正常并发处理；图片及完整视频都必须能在流运行期间取得有效结果。
两个文件 worker 存在、任务入队或流停止后文件才完成，均不足以证明满足要求。

| 项目 | 当前验收要求 |
| --- | --- |
| 实时有效输出 | G3 不低于 15 FPS，rfm 不低于 20 FPS，服务端输出与实际播放分别核验 |
| 持续性 | 两路连续运行并播放至少 30 分钟，文件任务的实际并发处理区间纳入统计 |
| 统计口径 | 每个 attempt 起点的完整、不重叠十秒窗口，保留启动、零输出及未达标窗口 |
| 延迟 | 服务接收至编码输出 P95 ≤ 2 秒、P99 ≤ 5 秒，且不持续累积；与采集至播放延迟分开 |
| 质量与完整性 | 不降低既定遮挡标准；离线保留全部帧、分辨率、PTS、音频及音画同步；推理异常失败关闭 |
| 验证环境 | 本地没有 CUDA；本地只做可执行的代码和契约检查，GPU 收益与并发正确性须在服务器验证 |

G3 正式验收沿用指定 RTMP 推流与 HTTPS FLV 播放路径 `26WY310002`；
`127.0.0.1:18554` 转发的内部 MediaMTX 路径用于诊断，不能替代该正式播放路径。
完成当前源的优化后，再补高 FPS 源验证双路每路至少 20 FPS，继续向 30 FPS 及以上推进。

降低文件并发、文件顺序执行、文件转 CPU、流高优先级而文件低优先级，均不作为优化方案。
先前向这些方向投入的实验偏离了当前并发目标；后续保持负载与业务契约，优化实际计算和执行效率。

## 当前进度与核心优化顺序

已有路线 A 实现、固定对照与候选的离线重复数据、GPU 媒体路径和实时混合负载证据可复用，
无需清零重跑。当前尚未通过混合负载下的逐窗口实时门槛、两路连续 30 分钟播放及绝对遮挡质量验收。
夜间侧脸连续漏遮与实时音频恢复仍分别未完成。

1. **先处理主车牌推理与局部复核的执行成本。** 最新服务器剖析中主车牌单次稳态主机耗时
   P50 约 38 ms、P95 约 54 ms；局部复核、跟踪重检也有明显长尾。六个主车牌采样中，
   主机 forward 为 33–49 ms，对应算子 GPU 活跃时间约 4–8 ms，同步 API 主机耗时约 8–18 ms。
   下一步把这些时间对应到模型内部算子、主机发射和等待位置，以及模型调用边界；
   查清具体关键路径后，只实现一个有整体收益依据的改动。不能把主机时间减去 GPU 活跃时间全算成可消除开销，
   也不能据此认定四个 worker 的上下文切换就是根因。
2. **检查同帧重复计算及调用边界的数据往返。** 按实际调用链核对预处理、裁剪、缩放、
   检测结果和复核输入的复用机会，保留新目标发现和既定确认规则。已存在的复用不重复建设；
   已回撤且无整体收益的预测表方案不原样重试。当前采样内搬运字节少、未见分配事件，
   不支持优先做泛化显存池或搬运带宽改造，也不能外推整个媒体链路没有复制成本。
3. **执行路径仍不足时，再选模型执行后端或透明合批实验。** 根据主车牌的实际动态控制流、
   小算子和发射成本，评估最小可行的后端优化或同模型合批；TensorRT、CUDA Graph、共享推理服务均不是必做项。
   合批必须同时验证吞吐、等待和公平性，不能使两个文件任务在业务上退化为顺序执行。
   不通过降检测频率、删复核或降低输入尺寸绕过当前质量问题。
4. **实时媒体问题按独立证据修复。** 对 G3 的输入等待、重连、处理停顿和外部播放积压分别归因，
   不将所有低 FPS 都解释为 GPU 竞争；内部 RTSP 诊断和外部 RTMP/FLV 验收保持区分。

每轮先使用相同完整素材和固定负载验证一个变量，确认收益超过波动，再进入两路流与至少两个 GPU 文件任务的
混合验证；最终固定版本完成正式路径长测、输出完整性和质量复核。模型内微基准变快不足以保留改动。
流与文件 worker 数、业务优先级、质量阈值不作为这轮实验变量。

目前已终止的方向：预测表复用未形成稳定整片收益，已回撤；局部人脸图执行和固定 I/O
未形成跨场景稳定整体收益，未接入；文件 CPU 隔离已回撤；流高优先级实验改动已移除且未部署。
错峰提交仅留诊断证据，不作为方案。历史 JIT 开关、骨干冻结等实验不在无新条件时重复。

## 已落地的实现

- HyperLPR 同帧视图合批候选已合入 main，保留原模型、分辨率、遮罩和质量规则。
- 实时路径保持 NVDEC/ GPU 预处理、GPU 遮罩和 NVENC，禁止 CUDA 失败静默回退 CPU。
- RTSP video-only 实验隔离了已复现的音视频 RTCP 时钟问题；音频处理代码保留，但恢复音频尚未验证。
- 实时非递增视频 PTS 会在有可靠帧间隔时推进到新的有效时间轴；原始 `source_pts`、`timeline_pts`、修复标志和修复次数均保留。无可靠间隔或存在音轨时仍失败关闭，离线时间轴约束不变。
- `POST /v1/stream-tasks` 增加可选 `max_bitrate`（bit/s）。省略或传 `null` 时不设置 NVENC `maxrate/bufsize`；显式值只影响实时流，幂等指纹和任务存储均包含该值。

## 离线结果

固定对照与当前候选的既有完整输出及三次重复证据均保留。已知首轮/重复结果显示：人脸媒体约 29.2–29.9 FPS，车牌媒体约 19.8–20.6 FPS，夜间媒体约 23.6–24.1 FPS；车牌和夜间端到端结果仍有低于 20 FPS 的运行。夜间入画侧脸连续漏遮仍存在，局部裁剪、填充、低分候选、EgoBlur 全图/镜像以及独立 YOLO12s 诊断均未形成质量修复；未放宽确认阈值，也未替换正式模型。

## 实时结果

### 时钟和音频隔离

本地 g3/rfm 探针保留了不同编码包相同 PTS 的证据；g3 的相同 PTS 包内容不同，不能静默丢弃。video-only 短测曾稳定运行，但长测仍发生源重连。外部 RTMP/HTTPS FLV 在 g3 源可达时已成功验证：3840×1080、PTS 递增、FLV HTTP 200，短段播放间隔正常。

### 码率控制

默认无码率版本在 g3 外部路径上最近样本估算约 20.6 Mbps，FLV 可解码。显式
`max_bitrate=20000000` 的实流验证也成功，最近样本估算约 11.9 Mbps，外部 FLV 30 帧无缺 PTS；两种实验均不是 30 分钟验收。

### 双路长测

默认省略 `max_bitrate` 的双路观察约 1860 秒，任务结束后活动任务为零：

| 流 | 结果 | 主要证据 |
|---|---|---|
| g3 | 三个有效 attempt，约 126/734/912 秒；两次源重连；各段窗口约 11.2–12.9、0.5–25.0、1.4–25.2 FPS；failed=0 | `data/validation/route-a-long-default-20261024-01/` |
| rfm | 单一 attempt 约 1849.8 秒；failed=0；窗口 4.6–40.7 FPS，包含低于 20 的窗口 | 同上 |

## 当前结论

路线 A 的实现、离线性能证据、实时 GPU 接线、异常 PTS 修复、可选码率控制和外部 RTMP/FLV 接口均已有可复现证据；路线 A **尚未通过**质量、当前 G3 稳定 15 FPS / rfm 稳定 20 FPS 的混合负载、双路连续 30 分钟和音画同步验收。

用户本轮已更新当前源的验证目标：G3 至少 15 FPS、rfm 至少 20 FPS，并在双路播放期间
正常处理图片和完整视频；完成当前优化后再补高 FPS 源。不再把更换输入源当作当前工作的
前置条件。质量问题、服务内部停顿和实际播放积压仍需处理，不能只把剩余工作归结为源帧率。
本轮两次混合负载实测、显式 5 Mbps 对照及缓存候选见
[双流与文件混合验证](live-mixed-validation-20261024.md)。不能用重连 attempt 相加或两路平均 FPS
替代逐路窗口门槛。

## 并发 GPU 设备剖析（2026-10-25）

在服务器 `62ad10f` 上提交两路实时流和两个 GPU 文件任务，观察记录包含 44 次四任务同时为
running/processing 的快照，首尾相隔约 115.7 秒。两个 4K 车牌文件任务均使用
`X-Detection-Profile: forward-primary-plate`，各成功处理 1776 帧；文件媒体耗时约 124.0–126.0 秒。
本轮未启动播放端采集，G3 在观察中出现两个 attempt；不能将任务状态快照写成四任务连续处理或播放验收。
剖析只用于定位，不计入吞吐验收。两个文件任务各有三个 primary-plate 设备采样摘要：

| forward 调用序号 / 源帧 | 两个任务的 host forward 范围（ms） | 对应算子 GPU busy（ms） | host synchronization（ms） | 同步 API 次数 |
| --- | ---: | ---: | ---: | --- |
| 64 / 184 | 33.5–41.1 | 7.5–7.6 | 8.2–18.2 | 各 31 |
| 424 / 697 | 47.4–48.6 | 4.0–4.1 | 14.4–14.4 | 各 33 |
| 768 / 1060 | 46.4–47.6 | 8.2–8.4 | 12.5–15.3 | 各 33 |

完整 host 计时还显示 `forward-primary-plate` 稳态 P50 约 38 ms、P95 约 54 ms，
`local-confirm` P50 约 8–9 ms、P95 约 46–48 ms，`track-recheck` P50 约 61–70 ms、
P95 约 133–134 ms。每份 1776 帧文件均有 1239 次主车牌 forward、1267 次 local-confirm 和
278 次 track-recheck；这些阶段存在嵌套和并行，累计时间不得直接相加。
采样内每次约 1143–1483 个 kernel，未记录显存分配 API 事件，不能外推为全任务无显存分配。
这些是模型局部采样，不是四个进程的 GPU 总利用率，也未证明性能差值可全部回收。

原始摘要与状态记录保留于 `data/validation/route-a-gpu-profile-mixed-20261025-02/`。
当前优先定位主车牌与局部复核中的同步、主机发射和重复执行成本；具体改动以关键路径证据为准，
保持两个文件任务和两路流的 GPU 并发要求，并按本文开头的验收口径验证。
