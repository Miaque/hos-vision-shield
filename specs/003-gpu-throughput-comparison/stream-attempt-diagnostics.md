# 实时 attempt 原因诊断（2026-10-25）

用户要求每次 attempt 切换都有原因；源故障与服务内部故障分开，后者必须定位修复。
现有 `process_stream` 在正常 EOF 后重连而不报告 failure，父进程又将多种恢复统一标为
`source_unreachable`，因此此前已结束的 rfm attempt 无法从现有记录确认原因。
该历史事实不改写为源故障，也不通过去除重连窗口使性能验收通过。

本轮复用 `GET /v1/tasks/{id}/diagnostics`，增加有界 `attempts` 及 `attempts_discarded`，
保留原 `last_failure`。每次尝试记录 run ID、generation、开始/结束时间；进入媒体处理后关联
FPS 统计使用的 attempt ID。保留最近 32 次，超出数量明确报告；每次结束也写 worker 日志，
验证采集器持续保存响应，避免只留最新一次。

结束记录区分正常源 EOF、源打开/读取错误、解码错误、输入时钟/队列、帧处理、编码、发布打开/写入/关闭、
发布控制请求、子进程退出以及 worker 控制中断。保留异常类型、原始 errno、HTTP 状态和调用位置；
异常文本可能含摄像头密码或 token，因此不透传文本、地址或请求头。
正常 EOF 记为 `source_eof`，不会变成无原因的成功退出；相同 I/O 异常按真实发生阶段归因。

worker 正常停机、停止请求、失租约与控制异常分别记录；若上个 owner 来不及写结束记录，
新 owner 将该未完成项明确记为 `worker_lost`，不推断为源错误。无法捕获内部异常的子进程退出保留返回码，
作为服务内部排查项，不能仅凭没有 Python 异常归为源故障。

本轮不改变检测、并发、重试退避或媒体处理策略；只修正原因记录及恢复状态中错误的统一源故障标签。
未来仍需现场验证：捕获真实 attempt 切换后，先依据直接阶段与错误码确认发生点，
再按证据判断源/传输或服务内部问题。原始发生点不自动等于最终根因，例如解码错误也可能来自损坏输入，
不能仅凭错误类型直接下结论。

本地验证：unit 集合 583 项通过、48 项按既有 GPU 条件跳过；随后新增的终态保存顺序回归在
9 项定向诊断测试中通过。覆盖正常 EOF、相同 I/O 错误的源打开/读取/解码/发布阶段区别、
HTTP 发布控制失败、凭据不进入记录、历史 32 项上限、旧 owner 中断、失租约与终态前持久化。
本地没有 CUDA；实际双流 attempt 记录及停止后的 Redis 持久化仍待服务器验证。

## 常规双流混合回归发现的停流顺序问题

`cd0633c` 部署后完成约 660 秒两路播放与三轮双文件，六份完整输出均匹配既有哈希，
两路均未自然重连，因此不额外等待重连，也不补写历史原因。
停止后 rfm 的 `stop_requested` 已持久化，G3 的外部 RTMP 记录只有开始项，缺少结束项。
证据在 `route-a-stream-attempt-reasons-20261025-01/candidate/diagnostic-verification.json`，
该诊断验证明确记为失败，文件完整性与诊断记录失败分别报告。

原因是外部发布者的 on_exit 回调可能先将任务转入 stopped 并释放所有权，
之后 run_stream 的 finally 再写结束项会被所有权检查拒绝。修复改为在该回调完成停流之前
先持久化结束记录，保持原有终态及所有权校验；原有停止后写入限制没有放宽。
新增测试先复现缺少 reason，再验证终态之后拒绝更新时结束记录仍已保存。
90 项定向测试通过、48 项按原条件跳过；后续 GPU 性能测试同时复核该顺序，无需专门等待自然重连。
顺序修复后的完整 unit 集合 585 项通过、48 项按原 GPU 条件跳过。

顺序修复已随 `b2e6ca7` 部署，并在后续单图 ROI 的 GPU 双流双文件采样中复核：外部 RTMP 与
内部 RTSP 任务停止后，diagnostics 均保留 `stop_requested`、结束时间和与 FPS 一致的 attempt ID。
服务器任务与队列收尾为空；证据位于
`route-a-single-image-pooler-20261025-01/candidate-device/final-verification-metadata.json`。
本轮没有自然重连；以后在正常性能测试中捕获并处理，不为等待重连单独延长诊断。
