## 低窗口定位与下一方向

rfm sequence=8302 的相邻成功输出相隔约 5.943 秒，记录的包接收只相隔约 0.000507 秒，
当前样本的包接收至输出约 6.035 秒。对应 API 区段中，source-read 增加约 5993.879 ms，
source-decode 0.550 ms，四帧 frame 合计 82.735 ms、inference 67.877 ms、encode 4.201 ms。
另一处 sequence=8693 的输出间隔约 4.831 秒，对应读包累计增加约 5400.170 ms。
这些是跨线程累计区段，不能相加成单帧成本或仅凭相近数字认定唯一根因。

代码在 demux 返回包后记录 received_at，并按 PTS 在解码释放该帧时取回；该时延可能包含
等待后续包、解码重排及缓冲停留。故“包已收到但延迟六秒”不能直接等同于 GPU 模型执行六秒，
也不能只凭 source-read 把所有责任归到摄像头。原始逐帧与阶段对照另存 gap-stage-investigation.json。

当前两路的 frame 增量平均约 24.54/20.06 ms，inference 约 20.58/16.82 ms；
主车牌 forward 平均约 9.10/7.40 ms、补车牌约 6.49/5.63 ms，均为 host 墙钟贡献，
存在嵌套/并行，不相加为总成本，也不由平均小于帧预算保证无低窗口。

下一步优先补齐“包接收 → 解码帧就绪 → 从缓冲取出/开始处理 → 成功 mux”的时刻，
在同一两路上分离读包/解码释放等待、排队与模型/遮罩/编码；再用图片和完整双文件验证竞争影响。
按证实的等待环节选择最小修复，保持不主动丢帧、不重复帧、原分辨率、检测和确认质量门槛。
本轮数据支持先定位这条等待链路，尚不足以把秒级停顿归为主车牌算力或固定 session 缓存问题。
