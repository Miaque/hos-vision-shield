# 双路实时与文件混合验证（2026-10-24）

## 本轮口径

用户更新当前源的目标：G3 独立帧脱敏后成功编码至少 15 FPS，rfm 至少 20 FPS，
两路继续向 30 FPS 优化；完成当前优化后再用更高 FPS 源复验。双路播放期间同时验证图片、
完整视频任务。使用每秒及从 attempt 开始的完整 10 秒窗口，不抹去启动和低窗口，
不以两路平均值、重复帧或丢帧补足门槛。服务接收至 mux 延迟仍检查 P95 ≤ 2 秒、P99 ≤ 5 秒。
播放端另记解码帧、PTS、帧间隔和时间轴积压；本地播放没有采集时钟同步，不能据此声称
摄像头采集至显示的绝对延迟。旧每路 20 FPS 记录保留其历史含义。

## 四项会话缓存候选

输出停顿与接收时间对齐后，可见部分帧在接收只相隔 0.03–0.08 秒时，编码输出相隔
0.8–1.8 秒，不能都归因于源断流。源码显示 YOLO/YuNet 的四项固定形状会话缓存按创建
顺序淘汰，反复使用的全图会话可能被变化的局部复核形状挤出；会话重建是候选成本，
尚不能将所有现场停顿归因于该机制。

本地 GTX 1080 使用同一 YOLO 权重、四项容量和固定形状访问序列：FIFO 两轮
2.653/2.802 秒、各重建 16 次；仅在命中时刷新顺序的 LRU 两轮 2.093/2.266 秒、各重建
13 次。各形状原始模型输出 SHA256 一致。这是隔离的缓存微基准，不能外推为 RTX 双路
FPS 提升。原始访问序列、逐次成本见 `data/validation/route-a-session-cache-20261024-01/`。

候选仅刷新已有缓存项的使用顺序，容量仍为四，不改变模型、精度、尺寸、质量阈值或
调度。回归测试先复现热点会话被淘汰，再检查热点保留、容量上限及禁止 CPU 回退；
服务器实际收益与混合任务回归仍需独立复测。

## 长测后固定形状人脸图执行原型

只在本地 GTX 1080、固定 YOLO 权重/FP32/禁用 TF32/禁止 CPU 回退下比较四种实际形状，
输入输出固定驻留 CUDA 地址；每种形状包含四个不同图像输入、四组 24 次交错运行。
384×1280、480×640、160×160、96×160 的原始预测最大绝对差均为零。后两种局部形状
普通执行中位约 5.25–5.40 ms，图执行约 3.57–3.91 ms；480×640 为约 4.65–4.68 与
4.20–4.22 ms。384×1280 后一组普通约 5.81、图执行约 5.54–5.64 ms，收益较小，
不混入第一组较慢数据夸大收益。首次捕获约 70–92 ms，需计入冷成本。

这仍是隔离推理原型，没有集成到主干或宣称 RTX 双路收益。进一步接入须覆盖会话线程归属、
固定缓冲区寿命、四项缓存淘汰、NumPy 局部输入、实际质量及采样诊断兼容性。原始结果见
`data/validation/route-a-ort-face-graph-20261024-01/report.json`。

## 图捕获并发限制与固定 I/O 对照

本地运行时为 ORT 1.20.2（build `8608bf02f2`）、Torch 2.14.1+cu126、GTX 1080。
首次捕获和真实 CUDA 补检并发时，只有确认观察到捕获活动的探针才作为并发证据：
`route-a-ort-face-graph-parallel-20261024-04/report.json` 中补检失败为
`operation not permitted when stream is capturing`，捕获失败为 CUDA 901。
此前未证明实际捕获重叠的两个成功探针不能写成并发兼容；第三个探针未观察到重叠，
也不计通过。全部在隔离进程执行，未修改服务执行路径。

上游 [1.20.2 捕获实现](https://github.com/microsoft/onnxruntime/blob/v1.20.2/onnxruntime/core/providers/cuda/cuda_graph.cc)
使用全局捕获模式，图状态按线程保存；
[会话执行实现](https://github.com/microsoft/onnxruntime/blob/v1.20.2/onnxruntime/core/session/inference_session.cc)
会在首次 API 调用中递归完成必要普通执行和捕获。不能把“两次 API 预热之后”误当成
首次捕获时刻，也不能假设初始化线程的捕获能直接供另一线程使用。这些源码用于解释
实验条件，实际兼容性以当前二进制探针结果为准。

另关闭图捕获，仅比较普通 CPU 输出绑定与复用 CUDA 输入/输出绑定，保持四种形状、
四个不同输入和交错各 24 次调用。预测最大绝对差均为零，但没有稳定收益：
480×640 普通中位 4.66/4.88 ms，固定 I/O 为 5.50/5.55 ms；160×160 普通
5.04/4.65 ms，固定 I/O 为 5.25/4.58 ms；384×1280 后段普通 5.73 ms，固定 I/O
5.81/5.92 ms。该原型未接入，证据 `route-a-ort-face-fixed-io-20261024-01/report.json`。

## 局部人脸预捕获的总处理收益复核

为避开运行期首次捕获冲突，另在初始化线程预捕获局部确认可能使用的九种 160px 形状，
只在同一线程的 NumPy 局部输入上重放，全图并行路径仍使用原会话。不同线程不得借用
这些图。以 barrier 同时启动真实补检和 24 次变化输入重放，两项均完成且预测逐位相同；
该探针未保存每次调用的重叠时间线，不能扩张为所有并发组合兼容的证明。

原型 `route-a-local-face-graph-20261024-01/02/03` 共计 1632 次帧处理，包含同一组车牌
45 帧、人脸 45 帧、夜间 12 帧的重复回放。所有对应帧的遮罩像素哈希、检测与跟踪计数
一致；这只是执行变化的等价检查，已知夜间漏遮仍在，不能认定质量通过。初始化九种图
的首轮额外成本约 1.981 秒，正式接入还需覆盖缓存寿命、显存、诊断和冷启动。

首轮交错结果部分包含跨场景会话重建成本。第二轮加入“常驻普通局部会话”对照，第三轮
改为逐场景完成整段预热后再运行普通/图/常驻/常驻/图/普通，每段 6 次，全部测量区间
会话缓存未命中为零。不能将首轮较大的差值全部归于图执行。第三轮处理耗时如下：

| 场景/帧数 | 原路径两次秒 | 局部图两次秒 | 常驻普通局部两次秒 | 局部图平均耗时减少 |
| --- | ---: | ---: | ---: | ---: |
| 车牌/45 | 6.228 / 6.327 | 6.293 / 6.282 | 6.389 / 6.299 | -0.16% |
| 人脸/45 | 5.798 / 5.894 | 5.818 / 5.806 | 5.887 / 5.874 | 0.57% |
| 夜间/12 | 1.468 / 1.464 | 1.408 / 1.402 | 1.446 / 1.448 | 4.19% |

局部前向自身确实缩短，但车牌、人脸总处理未超过原路径波动，夜间只有 12 帧且质量
未通过。常驻普通局部会话也未形成跨场景一致收益。因此两种局部候选均未进入主干执行
路径，没有为此部署或重跑双路长测；不能把本机短片数值写成 RTX 或端到端播放提升。
最终原型补齐 GPU 缩略图后完成；此前预热脚本的 Tensor/NumPy 类型错误不计有效运行。
