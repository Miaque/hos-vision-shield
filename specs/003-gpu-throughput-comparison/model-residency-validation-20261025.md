## 首轮串行的修复检查点 opt-20261025-03

Taskiq 0.12.4 的 Receiver 在取得预取额度之前就创建下一次 `__anext__()`，
即使配置 `max_prefetch=0`，忙 worker 仍可能从 Redis 领取下一条消息并留在本地等待，导致空闲 worker 无法领取。
隔离 Redis 与真实 Receiver 的回归已复现：忙 worker 持有第一任务时，第二个空闲 worker 无法启动第二任务。

修复在原生 worker 的领取层增加空闲门控：消息交给 Taskiq 前关闭门控，当前回调结束后才重新打开；
停止期间不重新开放。保留原 Taskiq 的回调、ACK 和队列流程，不增加全局串行锁，也不改变两个任务池的副本数。

旧实现的新回归失败，修复后相关集成通过；另验证停止时后续消息仍留在 Redis、没有被忙 worker 领取。
