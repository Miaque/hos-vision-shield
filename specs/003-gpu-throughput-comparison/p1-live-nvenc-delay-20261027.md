# 实时 NVENC 输出等待候选（2026-10-27）

固定算法对照仍为 `581c175`。本项的直接执行对照为已部署 `8fc978c`，
两条原任务、模型、输入尺寸、3/flow、遮罩、时间戳修复与码率请求均保持。
只改变实时 NVENC 的 `delay`，离线编码和 CPU 实时编码不变。

## 吞吐与延迟的取舍（用户于 2026-10-27 明确）

在质量、完整性和双路公平性保持的前提下，允许用合理、有界的延迟换取更高吞吐、
更快的整体处理和更稳定的播放。候选选择同时比较逐路有效 FPS、完整文件处理时间、
混合负载可用性、播放停顿、延迟分位及积压趋势；不把最低延迟作为单独的保留标准。

先以既定服务接收至输出 P95≤2 秒、P99≤5 秒且不持续积压作为实验预算，
按实际收益选择缓冲深度、异步执行或小批量。明确记录额外等待及启动成本，
不通过丢帧、重复帧、减少质量工作或隐藏低窗口换取表面收益。
若有充分收益需要调整该预算，另列具体延迟、收益和风险，不擅自改写原验收结果。

`delay=0` 仍是可比较候选：已测得待输出清零和时延改善，当前没有明显整体吞吐损失；
这不排除后续采用在预算内有更好吞吐的异步编码方案。仅增加等待、未改善吞吐或稳定性，
以及延迟持续累积的方案，都不作为有效优化保留。

## 选择依据与最小改动

新分段观测显示，两条流通常保留两帧 pending。G3 sequence=1731/1732 已在
单调时刻 4878105.196/4878105.281 开始处理，但直到后续输入在约 4878108.667 到达后，
才于 4878108.749/4878108.790 成功输出。单看 processing_to_output 的 3.55 秒，
会把等待未来输入释放编码包的时间与真实处理开销混在一起。

[FFmpeg NVENC 选项定义](https://github.com/FFmpeg/FFmpeg/blob/n8.0/libavcodec/nvenc_h264.c#L141)
将 delay 映射为 async_depth，默认上限很大；
[输出就绪判定](https://github.com/FFmpeg/FFmpeg/blob/n8.0/libavcodec/nvenc.c#L2582)
会根据 ready/pending 表面数量与该深度决定是否返回包。这支持以单个 `delay=0`
消除完成图片等待后续输入的假设，实际行为仍以当前二进制和硬件检查为准。

改动只在 `add_video` 的 live/CUDA 分支追加 `delay=0`。保留 p6、ull、vbr、cq=19、
bf=0、GOP、源时钟、颜色元数据与请求的可选码率。没有丢帧、重复帧、降分辨率或改检测规则。
代价是编码调用可能等待硬件完成，必须核对与模型/遮罩流水线重叠减少是否影响总吞吐。

## 本地 CUDA 组件证据

同一 4K 车牌原片前 16 帧，经 NVDEC、GPU 遮罩和 NVENC；只在内存原型改变 delay。
在第四帧后人为暂停提供输入 0.5 秒，保留所有帧和原 PTS，不将暂停计为处理性能。

| 项目 | 普通路径 | delay=0 原型 |
| --- | ---: | ---: |
| 暂停前尚未返回的帧 | 2 | 0 |
| 首次 encode 返回包数 | 0 | 1 |
| 全部输出包数 | 16 | 16 |
| 本次最大输入编码调用至包返回时延 | 约 0.532 秒 | 约 0.063 秒 |

两种方案 16 个 H.264 包的逐包内容 SHA256 和 PTS 完全相同；这是一段本地 GTX 组件检查，
不是 RTX、完整视频绝对质量或双流吞吐证明。证据在
`data/validation/route-a-nvenc-delay-20261027-01/`。

新真实 CUDA 回归先在普通实现上失败：首帧 encode 没有返回包。修正后检查 12 帧均在
本次 encode 返回、flush 无剩余帧，完整解码及 PTS 保持。编码参数、CPU/离线路径及
两个真实 RTSP/RTMP GPU 媒体检查共 18 项通过，包含 AAC/B 帧输入的既有媒体保护。

这是直接 FLV 到达与解码证据；浏览器呈现另起观测，不能由它宣称 30 分钟实际播放通过。
