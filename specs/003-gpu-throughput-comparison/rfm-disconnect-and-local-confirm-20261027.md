## 单变量实验：局部补人脸固定形状会话

局部确认保持 320px 视图、原 OpenCV 缩放与填充、权重、FP32、阈值、镜像确认及全部工作量。
NumPy 确认原走动态 YuNet CUDA session；固定形状普通 Run 有潜在执行收益，
但复用原四槽缓存会频繁淘汰。补充独立、最多 19 项的 320px 填充形状缓存，
与原四项大视图缓存隔离；非 320px NumPy 仍走原动态 session。
GPU provider 校验、禁止 CPU fallback 及有界淘汰均保留。
不使用 CUDA Graph、不新增后台线程、配置、模型或 API。

本地 64 对变化形状调用：动态总约 2.298 秒，固定普通 Run 加有界保留总约 0.538 秒，
只创建 7 种实际出现的形状；之前四槽方案 49/64 次未命中、总耗时更差，仍保留其失败结论。
这只证明局部执行组件，不代表整体吞吐或 RTX 已提高。

回归先在旧代码上 3 项失败，修正后相关 103 项单元检查通过。
真实 CUDA 验证全部 19 个填充形状的 NumPy/Tensor 交错、预测解码、缓存保留与 CUDA provider，
并通过四份已标注图片区域及主人脸全 CUDA 执行检查。
旧图片诊断测试依赖 DEBUG 的 candidate_timings，首次未启用 DEBUG 的失败保留；
显式 DEBUG=true 后原质量与 provider 断言全部通过，未删改断言。

三场景连续片段共 408 帧逐次处理，遮罩像素 SHA256 与检测/跟踪工作量一致。
第二轮恢复旧 _faces 和旧缓存策略作为对照，并逐模式预热：
车牌候选耗时约增加 0.93%，人脸增加 0.56%，夜间增加 0.34%，没有稳定整体收益。
因此只作为针对变化形状及长尾的实验候选，不能以局部加速宣称卡顿已修好。
已知夜间漏遮未修复，等价不代表绝对质量通过。
证据 route-a-detail-face-numpy-20261027-03/ 及 route-a-yunet-local-cache-20261027-01/02/。

需要比运行波动更可靠的收益才保留；无整体或长尾收益则回退，并保留实验报告。
不因增加缓存就认定源端断开已解决，不把当前 rfm 零输入的区间从原目标统计中删除。

实验候选 `7a09a8d`（tag `exp-20261027-a-local-yunet-cache-01`）经授权脚本部署确认，
采集先于部署启动，只有 deployment-confirmed.json 匹配实际提交且再观察 30 秒后才提交文件。
证据 route-a-rfm-local-cache-20261027-base-01/ 与 candidate-01/。

后续若能捕获慢局部调用的具体输入形状与等待来源，再按新证据决定是否重新评估，
不原样重跑本轮无收益实验。
