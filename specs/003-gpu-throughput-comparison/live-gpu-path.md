# 路线 A 实时 GPU 路径接续

## FIFO 背压

原 `StreamBuffer` 在满队列时丢弃最旧帧，取帧时又取最新帧并清空积压，
与本轮不主动丢帧约束冲突。现在满队列等待容量，按 FIFO 逐帧取出并唤醒生产者；
停止信号能在等待期间解除阻塞。缺少时间戳的输入仍单独计为输入丢失，
音频容量与时长上限保持，音视频按各自 PTS 配对。

影响范围仅为流缓冲与调用它的实时读取线程，不影响离线视频、检测或遮罩规则。
取消后的未输出帧不作为吞吐证据。背压可能把积压移到网络或上游，
需要后续接收至编码延迟、源时间戳和断流恢复测量，不能凭队列有界宣称低延迟。

先改回归，旧实现出现三项预期失败（满队列等待、停止解锁、FIFO 与音频配对）；
修改后 `tests/integration/test_stream_pipeline.py`、`tests/unit/test_stream_output.py`
共 14 项通过。真实本地编解码验证每组完整 12 帧，覆盖 RTSP/RTMP 输出与
无音轨、AAC、G.711 A/U 音轨；网络端点由本地媒体文件代替。

本步尚未部署，仍需 NVDEC/GPU 处理/NVENC 接通、编码输出计数与延迟观测、
异常保护统计及至少 30 分钟双路测试。现有实时路径仍为 CPU 编解码，
不能将这次本地队列和编解码检查称为 CUDA 或实时性能通过。

追加首帧检测超时及推理异常注入：在两种输出协议及四种音轨组合中均传播异常，
没有输出成功事件，实际输出文件不存在或为零字节，没有原始视频包放行。
上述两份测试合计 30 项通过。这里验证的是处理链阻止输出策略，
尚未证明服务器模型真实故障恢复、已开始输出后的恢复或 GPU 失败行为。

## 实时 GPU 接线候选

显式 CUDA 流在解码线程选回模型所在 CUDA 设备，再创建已有 `CUDAFrames` 和
禁止软件回退的 `hwaccel`。复用离线 NV12 GPU 转色、检测与遮罩，输出保持 CUDA 帧，
将 PTS 按首帧归零后直接交给 NVENC。格式、颜色、模型、解码及编码异常继续阻止输出，
不为失败的 CUDA 帧尝试 CPU 转换。原 CPU 路径仍由显式 CPU 配置选择。

NVENC 保留离线 `p6`、VBR、CQ 19 质量目标；实时使用 `ull`、零 B 帧和一帧 GOP。
离线仍用原 HQ、三 B 帧及源码率 VBV 配置。GPU 编码参数的实际支持和输出质量待服务器检查。
实时 redactor 读取已有内部 config 中的 interval/tracking；默认仍是 1/template，
API 到流任务的 3/flow 参数接通尚待后续完成，不暗中将默认行为改为已验收的路线 A。

流子进程输出编解码器、检测调度计数与已有阶段计时；流任务监督器保留这些字段，
以复用现有任务响应头。该元数据不单独证明 GPU 算子的实际执行或最终编码帧数。

本地先新增合约检查，旧实现出现六项预期失败：实时选择了 libx264，
CUDA 源未携带硬件解码参数。接线后设备/PTS/FIFO/首帧解码、遮罩、编码失败检查通过。
任务层使用独立 Redis 7.4.3 验证，两种输出协议的元数据检查在旧实现缺字段失败，
修复后相关任务/媒体定向检查共 78 项通过。最初因未配置 Redis 路径的两项 setup 错误
已通过指定现有本地 Redis 二进制解决，没有改用模拟存储。

追加 `RUN_GPU_TESTS=1` 的流测试入口，覆盖两种输出协议、四种音轨组合及推理失败，
使用真实 NVDEC、GPU 遮罩和 NVENC，以本地媒体文件替代网络端点，检测器为固定矩形。
本机未开启这些硬件用例。追加后编解码与流路径定向检查为 38 项通过、24 项硬件用例跳过；

## 实时编码输出和延迟采样（本地实现，尚未部署）

`stats.stream` 只在实时处理事件存在时返回，旧图片/文件 stats 字段保持不变。
输入计数是解码器交出的帧数（含无 PTS 的被丢弃帧）；处理数仍沿用提交编码的计数。
独立编码输出只有在输出 PTS 匹配已脱敏输入、视频包成功 mux 后才增加；重复或未知 PTS 包
单独计数，不增加有效帧数。记录编码缓冲待输出数、应用视频队列、音频队列字节、失败帧和保护帧。
现有策略是失败阻止输出，无整帧保护输出，因此保护帧为零；失败帧不能视为正常吞吐。

延迟从解复用器交出带 PTS 的压缩视频包开始，用有理数 PTS 匹配解码重排序后的帧，直到编码包
成功交给复用器。匹配表有界；未匹配接收时刻用 null 和累计 missing_receive_frames 明示，
不可用解码完成时间替代。该边界包含后续解码、应用排队、脱敏、编码和 mux 等待，
不包含解复用器此前的网络/内部缓存，也不是采集至播放延迟；还须检查源 PTS 相对输出时钟的漂移，
避免只看本地应用延迟漏掉上游积压。未观测到的网络丢帧不能从解码帧数推断为零。

每个子进程尝试都有独立 attempt_id。快照附服务端单调时钟，仅保留最近 512 个输出帧样本，
正常运行每秒报告一次，结束或失败时强制报告；避免逐帧重复发送整份样本。采集器应至少每秒保存
快照，并按 attempt_id/sequence 去重、验证连续性；漏采或收到新尝试 ID 必须单列，
不能把重连前后拼成无间断三十分钟。逐秒、十秒窗口和延迟分位数须由完整样本计算，
不能从 processed_frames 或 API 轮询间隔估算。长时间无更新须记录为停滞/观测缺口，不能当作零延迟。

编码待匹配表上限 512，超限停止处理；不会靠丢弃输入帧控制队列。输入接收时钟匹配表上限 256，
溢出仅导致延迟证据缺失，不丢视频帧；有缺失的运行不能声称完整延迟验收通过。

验证：新增计数器先因模块不存在失败，真实媒体检查先因 stream 统计缺失失败，
Redis/API 四个组合先因响应模型过滤字段失败，再完成实现。
完整本地 unit 加流 API/FIFO 检查为 550 通过、48 CUDA 跳过、1 项旧字段集合断言失败；
该断言改为验证实际默认响应仍仅含原三个字段（模型加载数据不泄露），随后连同全部本次
媒体、B 帧重排序、GPU 接线模拟、失败关闭、Redis/API 与 FIFO 定向检查共 92 通过、48 CUDA 跳过。
覆盖编码延迟到 flush、mux 修改 PTS、重复/未知包不计吞吐、失败 mux 不记成功、缺失时钟明确标记、
样本/编码积压有界及真实 AAC/G711 音轨兼容。没有在本机执行 GPU 硬件用例。

## rfm RTCP 时钟映射隔离

本地 GTX 1080 / PyAV 19.0.1（libavformat 63.1.102）使用与正式路径相同的
NVDEC 参数，五次独立打开各观察至多 25 秒。前两次分别在第 256、155 帧复现时钟回退，

队列或编码即可复现，故这些阶段不是这两次回退的起点。其余三次未复现，不宣称恒定失败。

进一步交错运行保留音视频、仅视频、保留音视频、仅视频四次独立探针，
保存每个包的 PTS/DTS 及 FFmpeg 暴露的 RTCP SR/PRFT side data，记录于
`data/validation/route-a-rfm-rtcp-probe-20261024-01/`。两个保留音视频的运行分别在
10.312、15.266 秒复现，两个仅视频运行各约 25 秒、642/649 帧未复现。

映射偏移 -0.206 秒；第二个失败点为 4.997 / 4.942 秒，偏移 -0.055 秒。
这些偏移超过相应帧间隔，触发已观测到的包与帧时钟回退。

[FFmpeg 的 RTP 解复用实现](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/rtpdec.c)
在收到 RTCP SR 且存在多个流时使用 NTP/RTP 映射计算 PTS；
[RTCP SR 字段定义](https://www.ffmpeg.org/doxygen/8.0/structAVRTCPSenderReport.html)
支持从已保存 side data 独立复核两类时钟增量。结合包级证据及交错条件，
当前证据支持 rfm 的 Sender Report 映射不连续导致此次解复用时钟回退；
不将其归因检测吞吐不足，也不声称已证明所有源、FFmpeg 版本或历史重连都有同一原因。

仅视频条件排除了原始音轨，不能作为正式修复或验收方案；生产路径仍保留音频、
原始时钟检查和失败后自动重连，没有通过丢弃回退帧、改写时钟或移除检查掩盖故障。
此处为本地故障隔离，不能代替 RTX 三十分钟双路验收；正式验收仍需可靠输入。
任何时钟恢复方案都须独立验证音画同步、有效帧和时间轴，不能未经验证就认定修复。
