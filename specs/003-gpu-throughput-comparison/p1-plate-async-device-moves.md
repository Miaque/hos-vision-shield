# 主车牌模型内部设备迁移实验（2026-10-25）

本轮只优化主车牌推理的执行路径。两路实时流与至少两个 GPU 文件任务并发要求不变，
不调整任务优先级、检测频率、输入尺寸、质量规则、模型权重或编解码策略。
路线 A 固定算法对照仍为 `581c175`，本轮直接运行对照为回撤版本 `62ad10f`。

## 已定位的成本

`route-a-gpu-profile-mixed-20261025-02/` 保留两份完整车牌文件的 profile、六份 CUDA trace、
下载文件哈希及 `primary-trace-analysis.json`。每次采样包含 31–33 次 CUDA 同步 API，
其中 16 次位于 Gen1 `move_device_like → aten::to → aten::_to_copy → aten::copy_`，
对应同步 API 主机累计耗时约 3.0–9.2 ms。它们来自五层锚框网格及 RPN 尺寸/层级元数据等小张量迁移，
不是文件任务的调度等待，也不代表全部时间均能消除。另有 nonzero、NMS、ROI 格式转换和
repeat_interleave 的同步，当前不改变其算法。

此前锚框缓存减少了十次上传，但在 RTX 整片测试无稳定收益，已撤回。本轮不缓存锚框或检测结果，
继续每次生成全部原始网格，只实验模型内部迁移的主机同步方式。

## 候选实现与边界

在已有 Ada 半精度车牌包装器中，复制原模型的内联图，仅把固定 Gen1 的 17 个
`aten::to.prim_Device` 节点的 `non_blocking` 改为 true；目标是所选 CUDA 设备，
后续计算仍位于相同模型流。17 个节点包含已经在所选设备上的入口迁移；采样中实际发生 16 次相关同步。
原模型方法图不被修改。原尺寸元数据继续留 CPU，输出框/分数继续为 FP32，
输出下载及 CPU 消费前的同步不变；模型内部候选数量、排序、NMS 和 ROI 计算均保留。

图匹配数量不符时初始化失败，不静默执行部分修改或回退 CPU。使用当前固定 PyTorch 的内部图接口，
升级模型或 PyTorch 后必须复验。生成内联图本身也可能改变执行开销，后续总收益不能全部归因于
移除复制后的同步；设备 trace 用于验证具体机制，整片与混合负载用来决定保留或撤回。

[PyTorch 非阻塞复制说明](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html)
描述了默认 to() 在复制后等待，以及 CPU→CUDA 与 CUDA→CPU 的不同同步要求；
本轮只改变前者。[图接口上游声明](https://github.com/pytorch/pytorch/blob/main/torch/_C/__init__.pyi.in)
用于核对当前内部图 API，不将其视为跨版本稳定接口。

## 验证与判定

- 新增回归先在旧实现失败；候选检查 17 个内部迁移、阻塞 CPU 输出复制、空/单项/变化尺寸、
  输入不变、原方法图不变和未知图失败关闭。
- 本地 unit 集合 575 项通过、48 项按原条件跳过；本地没有 CUDA。
- 固定 Gen1 的 FP32 CPU 图连接在 32×32、319×321、360×1280 上完整输出逐位相同；
  另检查有实际车牌输出的固定图片。这些不能替代 CUDA 半精度输出和性能验证。
- 服务器先在 `62ad10f` 完成两路流播放加三轮双文件完整处理，再以不可变候选 tag 测相同负载。
  两路门槛仍为 G3 15 / rfm 20 FPS，启动窗口及低值均保留；短轮不算 30 分钟验收。
- 每份视频核对全部帧、分辨率、有理数 PTS、AAC 内容/时间及输出哈希；候选若不一致则继续逐帧定位，
  不默认解释为数值误差或质量通过。
- 补独立设备采样验证同步是否减少。只保留超过运行波动的整体收益；不以算子或同步计时减少作为采用依据。

## 服务器执行证据（候选 `eed1331`）

不可变 tag `exp-20261025-a-plate-async-device-moves-01` 已部署；资源与 profile 指向同一块
RTX 6000 Ada，profile 中 `detection.egoblur` 的源码哈希与该提交一致，车牌参数为 FP16。

独立设备采样在双流与双文件负载下完成两个 1776 帧车牌视频，媒体耗时 119.852/120.842 秒。
六个对应采样的同步 API 次数均减少 16 次，从原路径的 31/33/33 变为 15/17/17；
主车牌稳态主机 P50 为 33.006/32.745 ms、P95 为 48.911/48.559 ms。
这些运行带 profiler，输入时段也不同，不用于判定整体提速。两份完整输出 SHA256 均为
`231cf162a86c3f945b4c2be30b710c235e8bacf41766c7c9f0e7d5d2c9cc2132`，
与本轮原版本的六份完整输出逐字节相同；检测计数一致，1776 帧及 943 个 AAC 包的完整性结论按精确哈希复用。
证据在 `route-a-async-device-moves-20261025-01/{candidate-device,device-comparison.json}`。

质量检查保留两类失败证据：第一轮对 JPEG 重编码输出错误使用无损像素断言，候选与原版本的 JPEG 输出
实际逐字节相同；改用相同解码像素的 PNG 输入后，8 份可用样例的必验/保留区域通过，
`rtsp-green` 必验区域仍失败，另有 7 份本地素材缺失。临时切回 `62ad10f` 对同一 `rtsp-green`
PNG 复测，原版本与候选 SHA256 均为 `03cb981c5b9aa3128b644b0b46cd039a06b253c4f360f6cc36970a8a8ac363d3`，
该区域深灰覆盖率均为 0.6875。此项是两版本共有的绝对质量失败，不能因输出一致判为通过。
证据在 `candidate-quality`、`candidate-quality-png`、`reference-quality-png` 及 `rtsp-green-comparison.json`。

普通混合负载原版本已完成三轮双文件，六份视频全部成功，平均媒体耗时 124.446 秒；
各轮四任务实际推进重叠约 125.3/122.9/103.1 秒。G3 两个 attempt 分别约 397.0/103.8 秒，
28/49 个完整窗口低于 15 FPS；rfm 单个 attempt 约 515.9 秒，0/51 个完整窗口低于 20 FPS。
G3 外部 FLV 播放连接在重连时退出，原版本不满足连续播放要求。候选普通三轮对照正在接续，
目前尚无普通混合负载整体收益结论，未宣布采用该候选。

候选首轮普通采集在约 237 秒因 HTTP `RemoteProtocolError` 中断，旧采集器的 finally 随后停止双流。
首对完整文件成功，媒体耗时 117.190/117.641 秒，输出哈希与原版本一致；第二对上传已返回原任务 ID，
保留 ID 继续观察和下载，最终成功，但其处理主要发生在流已停止之后，不能计为完整混合负载对照。
错误没有被解释为服务器任务失败，也没有重复创建这两个任务。

修正忽略目录内的采集脚本：GET/PATCH 的瞬态传输失败保留同一请求重试，记录错误，
关闭连接复用以规避已遇到的空闲连接断开；不自动重发上传 POST。MockTransport 自检确认
GET/PATCH 重试保持 URL 和请求体，POST 不重放。确认原进程终止、原任务收尾及队列为空后，
另存 `candidate_retry`，以相同版本、素材和负载补完整三轮；不将新旧运行合并成连续验收。
